# 单元 3：SDIE 前置阶段——从需求规约到设计

> 定位：可参考 · 可操作 · 可落地

---

## 一、为什么前置阶段最重要

在 SDIE 体系中，**前置阶段的质量决定了 AI 辅助编码的质量**。

```
模糊需求 → AI 生成模糊代码 → 大量返工
清晰规约 → AI 生成精准代码 → 一次到位
```

垃圾进，垃圾出（Garbage In, Garbage Out）在 AI 辅助开发中被放大了——AI 执行速度快，方向错了损失更大。

## 二、需求规约（Spec）

### 2.1 什么是需求规约

需求规约是将模糊的业务需求转化为**精确、可验证、无歧义**的技术描述的过程。

**规约前（模糊）：**
> 用户可以管理自己的订单

**规约后（精确）：**
> - 用户可以查看自己的历史订单列表（分页，每页20条，按创建时间倒序）
> - 用户可以取消状态为"待支付"或"待发货"的订单
> - 用户不能取消状态为"已发货"或"已完成"的订单
> - 取消订单后，库存自动回滚，若已支付则触发退款流程
> - 验收标准：取消成功后订单状态变为"已取消"，用户收到站内信通知

### 2.2 需求规约模板

```markdown
## 功能：[功能名称]

### 背景
[为什么需要这个功能，解决什么问题]

### 用户故事
作为 [用户角色]，
我希望 [做某件事]，
以便 [达到某个目标]。

### 功能描述
#### 正常流程
1. [步骤1]
2. [步骤2]
3. [步骤3]

#### 异常流程
- 当 [条件] 时，系统应该 [行为]
- 当 [条件] 时，系统应该 [行为]

### 验收标准（AC）
- [ ] AC1: [可测试的具体条件]
- [ ] AC2: [可测试的具体条件]
- [ ] AC3: [可测试的具体条件]

### 不在范围内
- [明确排除的内容，防止范围蔓延]

### 依赖
- [依赖的其他功能或服务]
```

### 2.3 用 AI 辅助写规约

```

Claude：[生成草稿]

Claude：[更新规约]

```

```

## 三、接口设计（API Design）

### 3.1 API 设计原则

**RESTful 命名规范：**

```
# 资源用名词，操作用 HTTP 方法
GET    /api/orders          # 获取订单列表
GET    /api/orders/:id      # 获取单个订单
POST   /api/orders          # 创建订单
PUT    /api/orders/:id      # 全量更新订单
PATCH  /api/orders/:id      # 部分更新订单
DELETE /api/orders/:id      # 删除订单

# 嵌套资源
GET    /api/orders/:id/items        # 获取订单的商品列表
POST   /api/orders/:id/cancel       # 取消订单（动作用子资源）
```

### 3.2 接口规约文档模板

```markdown
## POST /api/orders/:id/cancel

**描述：** 取消指定订单

**权限：** 登录用户，且只能取消自己的订单

**路径参数：**
| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | string | 是 | 订单 ID |

**请求体：**
```json
{
  "reason": "string"  // 取消原因，可选，最长200字
}
```

**成功响应 200：**
```json
{
  "code": 0,
  "data": {
    "orderId": "xxx",
    "status": "cancelled",
    "cancelledAt": "2024-01-01T00:00:00Z"
  }
}
```

**错误响应：**
| HTTP 状态码 | code | 说明 |
|------------|------|------|
| 404 | 1001 | 订单不存在 |
| 403 | 1002 | 无权操作此订单 |
| 422 | 1003 | 订单状态不允许取消 |
```

### 3.3 用 AI 生成接口文档

```

    输出 Markdown 格式的接口文档，包含请求/响应示例

Claude：[生成接口文档]

你：把这个接口文档转成 OpenAPI 3.0 格式的 YAML
```

## 四、数据模型设计

### 4.1 数据模型设计流程

```
业务概念 → 实体识别 → 关系梳理 → 字段定义 → 索引设计
```

### 4.2 实体关系描述模板

```markdown
## 数据模型：订单系统

### 实体

**Order（订单）**
- id: UUID, 主键
- userId: UUID, 外键 → User.id
- status: enum('pending_payment', 'pending_shipment', 'shipped', 'completed', 'cancelled')
- totalAmount: decimal(10,2)
- createdAt: timestamp
- updatedAt: timestamp
- cancelledAt: timestamp, nullable

**OrderItem（订单商品）**
- id: UUID, 主键
- orderId: UUID, 外键 → Order.id
- productId: UUID, 外键 → Product.id
- quantity: int
- unitPrice: decimal(10,2)

### 关系
- User 1:N Order（一个用户有多个订单）
- Order 1:N OrderItem（一个订单有多个商品）
- Product 1:N OrderItem（一个商品出现在多个订单中）

### 索引
- Order: (userId, createdAt DESC) — 用户订单列表查询
- Order: (status, createdAt) — 后台按状态筛选
- OrderItem: (orderId) — 查询订单商品
```

### 4.3 用 AI 生成建表 SQL

```
你：根据上面的数据模型，生成 MySQL 建表 SQL，
    包含适当的索引，字段加注释

Claude：[生成 SQL]

你：帮我检查这个数据模型，有没有遗漏的字段或者设计问题
```

## 五、技术方案设计

### 5.1 技术方案文档模板（ADR）

ADR（Architecture Decision Record）记录每个重要技术决策：

```markdown
## ADR-001: 选择 JWT 作为认证方案

**状态：** 已采纳

**背景：**
需要为 API 实现用户认证，系统是前后端分离架构，
需要支持移动端和 Web 端。

**决策：**
使用 JWT（JSON Web Token）进行无状态认证。

**理由：**
- 无状态，服务端不需要存储 session，便于水平扩展
- 前后端分离架构的标准方案
- 生态成熟，各语言都有稳定的库

**代价：**
- Token 无法主动失效（需要配合黑名单或短过期时间）
- Token 体积比 session ID 大

**替代方案：**
- Session + Redis：可主动失效，但需要 Redis 依赖
- OAuth2：适合第三方授权场景，当前不需要

**实施细节：**
- Access Token 过期时间：2小时
- Refresh Token 过期时间：30天
- 存储位置：前端存 localStorage（Web）/ SecureStorage（移动端）
```

### 5.2 用 AI 做技术选型

```
你：我们要实现实时消息推送，用户量预计10万，
    帮我对比 WebSocket、SSE、轮询三种方案的优劣，
    给出推荐和理由

Claude：[对比分析 + 推荐]

你：选 WebSocket，帮我写一个 ADR 文档
```

## 八、从规约到代码的交接

前置阶段完成后，把规约"喂给" Claude Code：

```bash

cp 用户积分系统规约.md docs/specs/

# 更新 CLAUDE.md，引用规约
echo "## 当前任务\n正在实现用户积分系统，规约见 docs/specs/用户积分系统规约.md" >> CLAUDE.md

# 启动 Claude Code
claude "根据 docs/specs/用户积分系统规约.md，
        先告诉我你的实现方案，不要写代码"
```

**Claude 有了清晰的规约，生成的代码质量会显著提升。**

## 九、常见问题

**Q：规约写到多细才够？**
A：细到"可以直接写测试用例"的程度。如果你能根据规约写出测试用例，AI 也能根据规约写出正确的代码。

**Q：设计阶段花太多时间，值得吗？**
A：前置阶段多花1小时，通常能节省实现阶段3-5小时的返工。特别是在 AI 辅助开发中，AI 执行速度快，方向错了损失更大。

**Q：需求变了怎么办？**
A：先更新规约文档，再让 AI 根据新规约调整代码。不要直接让 AI 改代码，否则规约和代码会逐渐不一致。
